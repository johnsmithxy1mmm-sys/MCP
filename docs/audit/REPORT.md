## 3. Три системные причины (не отдельные баги, а паттерны)

**П1. Проверка и действие разнесены, между ними — необратимость.**
`check_x402` (проверил отпечаток → расчитал у фасилитатора → пометил),
`create_watch` (посчитал → вставил), `maybe_anchor` (прочитал → отправил в чейн).
Локи есть, но каждый защищает только своё хранилище и отпускается между шагами.
Порождает INV-001, INV-009, INV-007.

**П2. Граница с внешним миром объявлена, но не проверяется.**
`Market.yes_price` документирован как «[0,1]», валидации нет; `_normalize_market`
проверяет тип внешнего списка, но не его элементов; `_canon_number` доверяет
любому числу из заголовка. Ответ площадки — недоверенный вход, но обрабатывается
как доверенный. Порождает INV-004, INV-005, INV-008.

**П3. Идентичность вызывающего берётся из данных, которые он же и присылает.**
`_client_id()` возвращает `x-client-id` как есть, и на этом строится вся
изоляция клиентов, лимиты и владение. Проверка `client_id != caller_id()`
сравнивает две подконтрольные атакующему величины. Порождает INV-002 и обесценивает
INV-009/A6/A7 как защиты.

мутаций в самых дорогих местах (см. `REGISTER.md`). Системный пробел — тесты
проверяют happy path и последовательное исполнение:

* ни один тест не запускает две операции **одновременно** (все 4 гонки прошли мимо);

Инварианты без единого теста: P6 (единицы измерения), N5 (монотонность времени),
M7 (fillable ≤ requested), устойчивость парсеров к враждебному входу.

## 6. Рекомендуемая модель идентичности (вы просили определить оптимальную)

Текущая модель («identity = заголовок от клиента») непочинима косметически:
любая проверка владения будет сравнивать данные атакующего с данными атакующего.
Оптимальная модель для этого продукта:

1. **Убрать `client_id` из URI ресурсов.** `portfolio://me`, `alerts://me` —
   владелец резолвится сервером. URI с чужим идентификатором приглашает IDOR
   самой своей формой.
2. **Идентичность выводить только из недоказуемого-подделкой источника**, в порядке:
   subject из проверенного OAuth-токена (`auth.py` уже готов) → адрес плательщика
   из **верифицированного** x402-платежа (криптографически доказан подписью) →
   иначе эфемерный идентификатор соединения.
3. **`x-client-id` понизить до подсказки-неймспейса внутри уже доказанной
   идентичности** (`{proven}:{hint}`), никогда — до самой идентичности.
4. **Персональные ресурсы отдавать только при доказанной идентичности.** При
   эфемерной — 403, а не «пустой портфель»: иначе лимиты (A6/A7) и лидерборд
   остаются накручиваемыми.

Побочный эффект: связка «платящий = владелец» естественно решает и биллинг, и
изоляцию, и лидерборд одним механизмом — платёж уже подписан.
